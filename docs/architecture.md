# Renderer architecture

## Data flow

1. The SFZ loader resolves paths and inherited parameters, reads sample metadata, and indexes regions by key and triggering MIDI CC. MIDI files become frame-ordered event streams.
2. The CPU walks the sparse MIDI events, tracks keyswitches and controllers, resolves triggers and voice choking, and describes each active voice as one or more spans with source positions and envelope parameters. It builds compact automation tracks for MIDI controls, LFOs and supported flexible pitch envelopes. Sample PCM is decoded only for regions that actually trigger in the batch, then uploaded once.
3. Each CUDA block renders a tile of one output. Threads run 48-tap Kaiser-windowed sinc interpolation, blend loop crossfades, evaluate envelopes, and mix channels with the requested stereo width and position. Variable pitch, filters and EQ keep state across spans of a voice. The renderer submits only the voices that need each recurrence and uses the CUDA multiprocessor count to spread independent voices across the device. Filter scratch stores one channel for mono sources. Static single-section filters carry their per-channel state in registers.
4. CUDA analyzes the float mix for `natural`, applies ClayEngine's mono tail finishing rules, and packs the accepted PCM16 frames. `orig` quantizes directly to stereo PCM16. `custom` bounds voice spans in the planner and applies any fade on CUDA. The GPU also records each output's peak and audible extent. The host downloads the final PCM and metadata, then writes the WAV, including any logical zero padding beyond the last planned frame.

The CPU prepares the first batch while CUDA initializes and plans the next batch while CUDA renders the current batch. WAV workers write earlier batches while both stages proceed. The renderer uploads only newly decoded samples at safe scheduling boundaries, keeping their offsets stable until a sample-bank reset. It reuses device scratch space and up to three page-locked host PCM buffers. On the batched fast path, PCM finishing and quality checks reuse filter and pitch scratch after mixing completes. Rolling jobs reserve finishing storage independently of their shared synthesis scratch.

`--cpu-batch-jobs` limits jobs per planning window, with the frame and sample budgets able to end the window sooner. Explicit volume groups stay in one planning window even if they exceed its job limit. `--gpu-batch-jobs` independently limits resident rolling jobs or jobs per actual CUDA batch. Both limits default to 64.

With audio quality enabled, GPU blocks measure the final PCM in 250 ms body windows and five 50 ms windows following each unique MIDI onset. The gate computes onset percentiles, body silence and clipping, and excludes failures before packing for transfer. Group volume uses body RMS and whole-track peak from the finished PCM. It selects a shared, peak-limited target on the GPU and applies gain while packing.

Job manifests can combine presets and explicitly named relationship groups. The planner keeps group members together and the renderer packs complete groups into a CUDA batch when the scratch estimate permits. On the batched path, complete groups require no waiting allocation or host round trip between synthesis and matching. Rolling group members release synthesis storage independently and retain accepted PCM until all group members finish. If a group spans batches, only accepted PCM from the earlier chunks is retained. Their statistics stay on the device. Scratch is immediately reusable, and an adaptive device memory limit controls retained PCM. Once the limit is reached, earlier chunks can stage PCM in host memory and upload it again for gain and packing. Earlier complete groups can be written while a split group renders.

## Device behavior

NVRTC targets the selected GPU's architecture when supported by the installed compiler. For a newer GPU it emits PTX for the latest available compatible target. NVRTC 12.4 and newer use four compiler optimization threads when the host has at least four hardware threads. The per-user kernel cache keys compiled code by source, compiler version and target flags so separate invocations can reuse it. If the cached module cannot load, the renderer compiles it again. Launch sizing uses the CUDA occupancy API.

The batched path adds free VRAM and reusable device scratch to estimate available memory. The batch budget uses the smaller of three quarters of that amount and one quarter of total VRAM. Synthesis reserves space for the complete mix, metadata, per-voice state, and finishing before budgeting reusable filter and pitch buffers. A batch that fits uses one segment. Larger batches build a cumulative timeline of actual active-voice storage and choose the longest successive intervals that fit the remaining scratch budget. Segment lengths can vary as voices enter and leave. Only voices intersecting the current segment receive intermediate storage and recurrence work. Playback phase, loop transitions, filter history, and coefficient smoothing continue across segment boundaries.

When recurrence work has queued successors, the renderer uses independent resident jobs instead of a fixed batch. Each job owns its mix, metadata, recurrence state, and finishing buffers. A shared filter/pitch allocation holds only the current intervals. Each round combines active jobs into common pitch, source, filter, and mix launches. Candidate intervals begin at a completion opportunity, grow to preserve parallelism across independent note chains, and shrink if actual intermediate storage exceeds the memory budget. This avoids fixed short slices that serialize work which could otherwise run concurrently across notes.

Completed jobs share tail and quality launches. Independent completions are compacted and downloaded together, carrying original job indices so out-of-order completion cannot associate a WAV with the wrong input. Synthesis storage is released before admitting successors. The CPU refill callback supplies ready planning windows without waiting while active GPU work remains; it waits only when the active set is empty. It uploads sample-bank growth before launching the next round. A fresh sample bank is deferred until the resident set drains. Whole-track mixes remain on the device for existing quality and tail rules. Volume groups keep their minimum-member, gain, and spill semantics.

Starting windows without recurrence work and single-job GPU limits retain the batched path. Refill is therefore a scheduling option for stateful queued work, not a guarantee of constant GPU utilization or an interrupt inside a running kernel. ClayEngine can continue submitting a single manifest per process; receiving additional jobs beyond that manifest still requires another invocation.

If device allocation fails, the renderer first reduces reusable synthesis scratch when that can lower the allocation, then retries smaller job batches. A single job can use CUDA-mapped host scratch. Exhaustion of that fallback produces a job-level `REJECT` with its output, MIDI, SFZ, and requested bytes. Subsequent jobs continue and a run containing only job-level failures returns status 2. Other CUDA errors remain fatal. `SEGMENT` diagnostics report segment count, reusable scratch bytes, and the corresponding whole-batch scratch demand. `SCHEDULE` reports submitted jobs, scheduling rounds, and admissions made while another job was resident. Explicit device allocation peaks and CUDA event timing are reported separately from wall time.

One process uses one CUDA device. Job manifests share the sample bank across presets, deduplicating samples by their canonical paths. Repeated references reuse the result of path resolution within the invocation. When the cache reaches a device-derived threshold, the CPU starts a fresh decoded bank at the next planning boundary while the GPU finishes the previous work with the old bank. The sample bank normally stays on the device across repeated passes. If the device allocation fails for lack of memory, the renderer places the active bank in CUDA-mapped host memory. Group PCM staging applies separately to finished tracks waiting for partners.

## Upstream references

ClaySampler uses its own parser, MIDI event planner, batch layout, and CUDA implementation. We used sfizz 1.2.3 as the reference for observable behavior, including its windowed-sinc approach, default CC mappings and master gain, envelope curves, and bend interpolation. The implementation does not include sfizz source or link sfizz at runtime. The comparison harness invokes the reference CLI separately. libsndfile is loaded as an external runtime dependency.

ClayEngine's `instruments/midi_render.py` and `instruments/render_tail.py` are the behavioral references for `natural`. ClaySampler prepares the events in memory and implements the float stop criterion and PCM16 mono finishing on CUDA.

ClayEngine's `instruments/reference_quality.py` and `instruments/melody_volume.py` are the references for the optional audio gate and group matching.
